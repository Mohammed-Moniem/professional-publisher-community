# v0.2: setup, review and recovery

All examples here are fictional. No real account, credential, screenshot or private writing profile is included.

## First run

Install Node.js 24+, npm and your chosen local AI client. In a reviewed clone run:

```sh
node scripts/setup.mjs setup
```

The wizard detects Codex and Claude Code, offers a client, installs locked dependencies, builds, installs Chromium, runs diagnostics, generates configuration, and registers only this plugin. An existing marketplace pointing to another clone is a blocking conflict; run maintenance from that clone. It preserves other registrations. Setup does not install system Chromium libraries on Linux; install those using your distribution's package manager if doctor/rendering reports missing libraries. Video validation also needs `ffprobe` on PATH.

For automated software setup, use `--client codex --yes --skip-connect`, or `claude` / `config`. `config` generates mergeable client files without changing client registrations. `desktop` likewise generates configuration and explains how to install the matching MCPB; desktop UI installation is still performed by the user. No secret goes in a command argument.

Open a new Codex/Claude task and ask it to call `get_workflow`, `diagnostics`, then `check_capabilities`. Open the private dashboard from `open_dashboard`. In Accounts, choose an account label and personal/company mode, then **Start secure connection**. Follow [onboarding](ONBOARDING.md) to create your own LinkedIn app and authorize it. Token refresh works only when LinkedIn actually grants a refresh token.

Fictional checkpoint:

```text
Software: ready                 Account: disconnected
Renderer: ready                 Worker: not installed
Client: Codex                   Live publishing: not tested
Next: open the private connection form and authorize your own app.
```

## Review workspace

Ask the assistant to prepare a local draft, then open Drafts. Select the destination, edit the caption/link, reorder or remove attachments, and update image descriptions. Save a new immutable revision and compare its text with the previous version. To add new attachments, ask the assistant to create a revision with those local files. Each saved version has its own digest; old approvals do not transfer. A schedule for the previous version stays attached to that version.

Inspect every individual slide under Slides, or open an attached PDF/video from Drafts. Record source notes and check facts, destination and attachments. **Approve this text for voice learning** is separate from **Publish this exact post publicly**. Unsaved content changes disable both actions until a revision is saved. Publishing uploads attachments and may require waiting for media processing before another explicit attempt. Published and uncertain drafts cannot be submitted again.

```text
Previous version            Current version
Original opening…           Revised opening…

Destination: Alex Example · personal profile
Visibility: PUBLIC
[ ] Facts and sources checked
[ ] All attachments/slides inspected
[ ] Destination checked

[Approve text for learning]   [Publish this exact post publicly]
```

## Voice Studio

Opt into learning before importing selected samples. Each observed writing rule cites eligible samples belonging to that identity. Unknown authorship, reshares and truncated examples cannot support new observed rules. A stable subset of original/commentary examples is held out for evaluation; approved edits remain training examples. This split applies to v0.2 rule generation, not retroactively to older flat profiles that may already have seen those examples.

Use manual preferences for corrections such as “Avoid rhetorical questions.” Enable/disable individual rules, inspect their evidence, and save a version. Counts describe available evidence, not model accuracy. Freeze protects the saved profile from further changes. The assistant applies enabled manual rules ahead of inferred preferences. Comparisons store three versions of the same brief and your chosen preference; no external AI service runs in the background. Reset removes voice rules, samples, versions and comparisons.

## Calendar and notifications

The monthly grid displays dates in the browser's local zone; every job also shows its approved IANA zone and ISO instant. Drag a pending job onto a date, or choose Reschedule. Review the proposed ISO time and UTC offset, particularly across daylight-saving changes, then explicitly approve the new time. Dragging alone never publishes or changes a schedule. Running, published and uncertain jobs cannot be moved.

Enable native notifications in Accounts or run `node scripts/launch.mjs notifications on`. Disable with `off`. Messages contain only generic job outcomes. macOS uses the OS notification service through AppleScript, Windows uses WinRT toast notifications, and Linux uses `notify-send`. Permissions, Focus modes, an interactive desktop session and installed OS utilities affect delivery. `submitted_to_os` means the OS accepted the request; it does not prove the notification was seen. Failures remain in the dashboard, and delivery is attempted at most once. Enabling notifications does not install the worker; use the existing opt-in worker setup separately.

## Disconnect and remove local voice data

Accounts → Disconnect disables the connection, cancels its pending jobs and deletes tracked credentials, including the current generation and pending setup credentials. It cannot recall requests already sent. Revoke the app separately in LinkedIn settings to invalidate the grant at LinkedIn. Reconnect through the same account label when needed.

Credential cleanup removes old generations tracked by v0.2. The current generation from v0.1 is adopted, but older untracked v0.1 entries cannot be enumerated portably and may need manual removal from the community credential service. Stop old v0.1 clients first. Voice-data removal clears only the selected identity's samples, voice and brand. Drafts and receipts remain to preserve duplicate prevention. Disconnect all accounts and remove the worker before deleting the entire private data directory manually; doing so loses every local publishing guard. Existing exported files and backups must be removed separately when deleting private data.

## Encrypted backup and restore

Accounts → Encrypted backup asks for a passphrase only in the private local form. CLI alternatives:

```sh
node scripts/launch.mjs backup
node scripts/launch.mjs restore /absolute/backup.ppcenc /absolute/new-workspace
```

The CLI reads a hidden passphrase from the terminal. Never place it in chat, environment configuration or command arguments. Files use a versioned envelope, scrypt-derived key and AES-256-GCM authenticated encryption. Records, local media and deck assets are included; credentials and older backup files are excluded. The current in-memory format supports at most 512 MiB per backup and needs available memory above that size. A forgotten passphrase cannot be recovered.

Restore requires a new directory and never merges into an active workspace. It relocates asset paths, retains published/uncertain guards, converts interrupted publishing to uncertain, removes review/learning approvals, cancels pending/running schedules, and requires reconnecting accounts. It does not activate a worker. Stop clients and point `PUBLISHER_COMMUNITY_HOME` at the restored directory to use it; do not run old and restored workspaces simultaneously against the same account labels. Reconcile posts created after the backup first: no old backup can contain newer receipts. Reinstall the worker explicitly for the restored location only after reviewing jobs. Plaintext source files and the active database still rely on OS disk encryption.

## Upgrade, rollback and uninstall

For a clean source clone:

```sh
node scripts/setup.mjs upgrade --tag v0.2.0 --client codex --yes
node scripts/setup.mjs rollback --client codex --yes
node scripts/setup.mjs uninstall --client codex --yes
```

Use `claude` for Claude Code. Upgrade fetches the explicitly selected tag from the official origin, records the previous commit in ignored `client-config/maintenance.json`, checks out the tag detached, and runs that version's setup. It refuses dirty trees. Rollback uses the recorded commit; database downgrade guards still apply. These are source-code operations, not automatic binary updates. Retain the previous clone/bundle and an encrypted backup before changing versions. The v0.2 rollback runner also handles v0.1's older setup layout; after rolling back, that older checkout does not contain the v0.2 maintenance command.

Uninstall removes this plugin from the selected client and removes the worker if this workspace records it as installed. It retains credentials, private data and the source directory. Disconnect first if credentials should be deleted. Other clients' registrations are untouched. Claude Desktop extensions are removed through its Settings UI.

## Verify signed release provenance

v0.2 main-branch CI signs build provenance using GitHub artifact attestations. Release promotion verifies these attestations and checksums before uploading. Download the artifact and matching `.sha256`, then use a current GitHub CLI:

```sh
node scripts/verify-release.mjs /absolute/path/to/downloaded-artifact
```

The check fails if provenance, signer workflow, repository or checksum does not match. It requires network access to GitHub's attestation service. The v0.1 artifacts predate this workflow and will not pass this check. GitHub provenance verifies which workflow built the exact artifact; it is not Apple Developer ID notarization, Windows Authenticode signing, or a security audit. Native platform signing requires separate publisher certificates and distribution setup, which are not configured for this preview.

References: [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations), [Apple Developer ID](https://developer.apple.com/developer-id/).
